# Правила работы с репозиторием

## Обновления сайта («Что нового»)
Каждое изменение, заметное пользователям (новая функция, исправление, изменение интерфейса), должно сопровождаться записью в `supabase/sql/releases/YYYY-MM-DD_<версия>.sql`:
вызов `public.add_site_release(версия, заголовок, пункты, дата)`. Образец: `supabase/sql/releases/2026-10-14_0.2.0.sql`.

- У каждого пункта есть `min_rank` — кому он виден: `1` все, `2` админы по предметам и выше, `3` админы и выше, `4` только главный админ.
  Пункты про управление пользователями, статистику и т. п. делайте с `min_rank >= 3`.
- У каждого пункта есть `scope` — где изменение: `site` (сайт, по умолчанию), `bot` (чат-бот Telegram), `app` (мини-приложение). Кнопка «Что нового» в боте показывает только `site`, а бот сам рассылает **все** пункты новой версии (по роли пользователя) — поэтому `scope` указывайте точно.
- Текст пункта — одной фразой, понятной пользователю этого уровня, без технических деталей.
- Повышайте версию в `package.json` вместе с записью. Повторный запуск файла безопасен.
- Записи можно также вести через форму на вкладке «Что нового» (главный админ).

## Термины интерфейса
Во всех текстах сайта слова значат одно и то же — не заменяйте их синонимами:
- **билет** (он же **вариант**) — один экзаменационный лист; **набор** — группа билетов, созданная за одну генерацию (хранится в «Архиве билетов»).
- **партия** — один импорт вопросов (файл или вставленный текст); «откатить партию» скрывает её вопросы из банка. Билетов это слово не касается.
- **экзамен-кластер** — тестовая книжка из четырёх предметов (раздел только для главного админа).
- **мини-приложение** — страница бота внутри Telegram; писать «Mini App» можно только вместе с пояснением.
- **банк вопросов** — все вопросы сайта; **корзина** — удалённые вопросы, которые можно вернуть.

## Тёмная тема
Включается классом `dark` на `<html>` (выбор пользователя, по умолчанию светлая). Стили лежат в `src/dark.css` и **создаются автоматически** по цветовым классам Tailwind из кода (`scripts/gen-dark-css.mjs`).
После добавления новых цветовых классов (`bg-…`, `text-…`, `border-…`) выполните `npm run theme:dark` и закоммитьте обновлённый `src/dark.css`. `src/game` и `src/tg` в генерации не участвуют — у них своя тема.

## Схема проекта
Перед работой прочитайте `docs/ARCHITECTURE.md`: там карта каталогов, модель данных, роли, главные потоки, правила деплоя и ловушки. Открывайте только те файлы, на которые она указывает, и не перечитывайте весь код.
Если вы меняете структуру (таблица, модуль, поток данных, ключ кэша, правило деплоя), обновите `docs/ARCHITECTURE.md` в том же коммите.
Перед выбором версии релиза сделайте `git fetch`: в `main` пушат параллельно, номера версий занимают быстро.

## Импорт сборников (право, история и т. п.)
Когда пользователь даёт сборники тестов и ключи (docx, русская и таджикская версии), действуйте по этому порядку без напоминаний. Рабочие скрипты и заметки держите в `scratch/` (в git не идёт); образцы — `scratch/law4`, `scratch/ch5` (`parse2`, `merge`, `dups`, `keys`, `build_final`, `insert`, `verify`).
1. **Разбор.** По каждому параграфу (§) читайте «Контрольные тесты» и «Тесты НЦТ»; варианты A–D (кириллические А/В/С/Е считайте латинскими), соответствия — 4 левых (A–D) и 5 правых (1–5), ключ соответствия — 4 цифры. Ключи — таблицы №/ответ. Большие XML разбирайте линейно (старый разборщик на ключах истории зависает).
2. **Синхронность RU ↔ TG.** Проверьте для каждого задания: условие, все четыре варианта и их порядок, цифры и даты, ключ RU = ключ TG, число пунктов. Расхождение — не править молча, а показать пользователю.
3. **Ключи.** Прочитайте и проверьте по смыслу **все** ключи (не выборочно). Фактические неточности самого сборника не исправляйте: импортируйте как в сборнике и перечислите их пользователю в конце.
4. **Дубли** (одинаковый факт и тот же правильный ответ, даже с переформулировкой):
   - в **одной теме** — оставить одно задание, остальные не импортировать (из пары К/Н обычно удаляется «Н»);
   - в **разных темах** и с банком (в том числе с прежними главами) — **связать** через `linked_ids`: у нового задания ссылка на существующее, между двумя новыми — ссылки в обе стороны (id задаются заранее);
   - разные вопросы с одним ключом (разные категории, «Какое событие РАНЬШЕ?» с разными вариантами) дублями не считаются.
5. **Вставка.** Сначала сухой прогон (`insert.mjs` без `--go`), затем `--go`. Новая глава «Глава N» (`order_index` N), темы «RU / TG» (`order_index` = номер §), источник «Сборник … (Часть N)», партия в `import_batches`; соответствия: сначала правые пункты, потом левые. После вставки — `verify.mjs`: сверка с final.json и ключей прямо в базе, должно быть 0 расхождений.
6. **Релиз** (см. выше): пункт на каждый предмет с числом тестов и соответствий и разбивкой по темам. В итоговом ответе назовите число импортированных заданий, удалённых дублей, связей и сомнительных мест сборника.
